# 大脱獄：ゲームフロー・看守監視v1.2・看守視界v1.0

Unity `6000.6.6f1` / C# の既存プロジェクトです。DEV-TURN-001 のゲームフロー基盤と SYS-GUARD-001 v1.2 の監視山札・公開履歴・履歴画面に、SYS-VISION-001 v1.0 の視界計算を接続しています。今回のブランチは `codex/sys-vision-001-v1-0` です。最新 `origin/plan-main` から作成し、依存する監視v1.2コミットを引き継いでいます。

監視山札の確率・構成・履歴管理はv1.2を維持しています。本番スキルカード・山札構成は未提供のため、既定シーンの対局開始は引き続き「仕様・設定の確認待ち」になります。製品版の対局全体が完成した状態ではありません。視界の幾何計算はSYS-VISION-001に従い、未確定のフィールド・柵データ対応と囚人の詳細な状態管理は暫定アダプターとして区別しています。

## 起動・設定

1. Unity Hub から Unity `6000.6.6f1` で開きます。
2. `Assets/Scenes/Daidatsugoku.unity` を開き、Play を実行します。
3. 盤面と UGUI は実行時に生成します。既存シーン・カメラ・クリック入力の参照は維持します。

シーン作成メニューは `Tools > Daidatsugoku > Create Prototype Scene` です。既存シーンを上書きしないため、通常は作成済みシーンを開きます。Unity の Build Profiles から同シーンを対象にビルドします。

試作フィールドの参照を再設定する場合は、Playを停止して `Tools > Daidatsugoku > Configure Prototype Guard Vision` を実行します。`GuardVisionSceneSetup.ConfigurePrototype()` が試作用アセットとシーン参照を設定します。この設定は正式なフィールド仕様を確定するものではありません。

設定項目は以下のとおりです。

| 設定先 | 内容 |
|---|---|
| `GameManager.playerCount` | 2～4人、既定3人。開始時にランダムな固定手番順を決定。 |
| `GameManager.skillCards` | `SkillCardDefinition` 派生型の本番カードアセット。枚数・条件・効果はカード仕様に従う。 |
| `GuardSystem.monitoringSource` | 任意の `GuardCardSource` 派生型による上書き。未指定なら v1.2 の標準監視山札を使用し、本番監視用アセットの設定は不要。成功した最初の監視以降の変更は次回 `ResetDeck()` から適用。 |
| `GuardVisionSystem.Field` | `GuardVisionFieldDefinition`。行数・列数・初期基準列・TOP/BOTTOMを明示したフィールドデータ。未設定・不整合の場合は仕様待機。 |
| `GameManager.flowPolicy` | `TurnFlowPolicy` 派生型。初回対応権、対象なし/複数対象、複数所有者順などの確定仕様を渡す。 |
| `GameManager.actionRules` | `NormalActionRules` 派生型。未指定時は `PrototypeActionQuery` が既存盤面ルールへ問い合わせる。 |

本番スキルカードと未確定の対応方針は、抽象型だけでは設定完了になりません。Editor 検証のカード・監視上書き・優先順位フィクスチャーは、それらの本番仕様の代用にしません。

## 看守監視と公開履歴

- 監視山札は30枚。生成ごとに監視率20・30・40・50・60・70・80%から独立に1/7で選びます。同じ率が連続することもあります。
- 見とる枚数は順に6・9・12・15・18・21・24枚です。残りを見とらんとして、生成時に Fisher-Yates で一度だけシャッフルします。消費中には再シャッフルも独立した結果抽選もしません。
- 看守ターンに1枚消費し、31回目の判定直前に新しい山札を生成します。30枚目の結果・履歴は保持し、新しい山札から余分なカードを消費しません。
- `TryDrawMonitoring(round, ...)` へ同じラウンドを再要求すると、確定済みの結果を返します。山札消費と履歴追加は一度だけです。初期化では履歴と判定済みラウンドもリセットします。
- `PublicHistory` が返す公開値は `GuardHistoryEntry.SequenceId`、`DeckId`、`CardIndex`、`Result` のみです。監視率・山札配列・残りの内訳・次回結果はUIに渡しません。
- 画面右上に常時表示される「監視履歴」から、全画面の半透明オーバーレイを開閉できます。全件を時系列で表示し、山札番号の区切りと通算番号・山札内番号を付け、長い履歴は縦にスクロールします。
- 仮デザインは黒70%の背景、赤 `#DC2626` の見とる／緑 `#16A34A` の見とらん、白太字の縦書きです。装飾・ブラーはありません。`GuardHistoryTheme` で色・寸法・余白・文字サイズを変更でき、判定ロジックには影響しません。
- 履歴表示中は履歴画面への入力だけを受け付けます。開閉によるドロー・ターン進行・時間停止は行いません。オンライン／オフラインの進行制御は本仕様では未確定です。

## 看守視界と監視への接続

- 座標は `VisionCell(Row, Column)` で表し、上から下・左から右へ増える0始まりの論理座標です。Unityの既存囚人座標は、`Cell.y` を行、`GridManager.GlobalColumn(Cell)` を列へ変換します。
- `GuardPosition` は基準列とTOP/BOTTOMを保持します。初期値はフィールドから読み、ランダム配置しません。`GuardVisionSystem.Flip()` は方向と常時表示だけを切り替え、監視抽選・発見処理を起動しません。
- `GuardVisionCalculator` はUIやUnityに依存しません。距離 `d` に対して左右へ `(d - 1) / 3 + 1` 列広げ、盤面外を切り捨てます。TOPの距離は `row + 1`、BOTTOMは `rowCount - row` です。
- 基本視界を先に求め、その中の柵だけを抽出します。各列で看守に最も近い有効な柵を採用し、TOPは柵のマスを含む下側、BOTTOMは柵のマスを含まない上側を遮蔽します。視界の計算結果は重複のない集合です。
- 看守ターンは、監視カード抽選 → 許可された割り込みの解決 → 最終結果確定 → 視界スナップショット → 全発見対象の通知、の順です。「見とらん」または監視無効の場合は視界計算・発見通知を行いません。
- `IGuardVisionSnapshotService` により発見判定1回につき最新の盤面・看守・柵から1つの視界スナップショットを作ります。通常のプレイヤーターンでは毎フレーム計算しません。
- `GuardSystem.PrisonersDiscovered` は全対象を変更不可のリストで一括通知します。囚人状態更新は `IGuardPrisonerService`／`IGuardPrisonerBatchService` へ委譲し、既定アダプターは既存 `Prisoner.Capture()` を使用します。除外された囚人は再配置できず、脱獄人数にも加算しません。

監視への割り込みは、カード側が `CanInvalidateGuardMonitoring` を明示し、`CanPlay()` の条件と外部 `TurnFlowPolicy` の対応計画を満たす場合だけ対象にします。この印だけで使用タイミングや優先権は定義されません。新しい本番カードや未確定の割り込みルールは追加していません。旧所有者別の看守対応コードは互換用に残し、標準フローからは呼びません。

### 暫定フィールド対応

`Assets/Settings/PrototypeGuardVisionField.asset` は既存25マスの段差盤面を引き継ぐ仮データです。5行・7列の全体座標範囲、初期列3・TOPは既存配置を維持する設定であり、正式な盤面仕様の確定値ではありません。視界計算後、実在しないマスを除外します。

既存の横向き共有境界で `Line == row` の柵を、その実在マスの前面柵へ変換します。縦向き柵や実在マスを伴わない外側境界は、正式な対応規則が未定義のため視界入力から除外します。柵の設置・破壊・移動ルールは変更していません。フィールド・柵仕様が確定したら、この対応部分を差し替えます。

### 開発用の視界確認

`GuardVisionDebugDisplay` のInspectorで `Show Vision` を有効にし、コンポーネントのコンテキストメニュー `Refresh Vision Debug Snapshot` を実行して、SceneビューのGizmosを確認します。看守の位置・前面柵・最終視界を表示します。反転・柵変更後は明示的に再実行してください。

初期状態では無効です。通常のGameビューに視界色分けを追加せず、デバッグ描画から発見処理も呼びません。看守の上下の位置表示は常時更新しますが、反転アニメーションはありません。囚人の跳躍・震えのパラメータと除外タイミングは未確定なので、通知イベントだけを用意しています。

## 進行と操作

初期手札0枚、盤上囚人0人、累計脱獄0人、ラウンド1で初期化します。各プレイヤーは既存どおり未配置囚人3人を持ち、初期柵は既存配置を使用します。最初のターン開始時からドローするため、操作可能時点の手札はドロー後の枚数です。

- 各ターンに「囚人配置」「囚人移動」「柵設置」「柵破壊」の可能な行動を1回実行します。
- 可能な通常行動がある間は終了・パス不可。宣言後に妨害されても消費します。
- 通常行動後は自動終了しません。カードを使用し、未解決処理がなくなってから「ターン終了」を押します。
- 通常行動不能でカード使用可能ならカードまたはパスを選択。両方不能ならドローと効果解決後に自動パスします。
- 「手札を開く」で所有者とページを選択します。使用可否は各カードの発動条件に従います。
- 超過時は新しく引いたカードも含め5枚以下になるまで任意に捨てます。対応中は対応者のカード選択・パスを表示します。
- 全員終了後に看守ターンへ進み、監視への許可された割り込みを解決してから視界と全発見対象を確定します。すべて完了後に次ラウンドへ進みます。
- チェーン解決後に脱獄を最終確定し、累計3人で即時勝利。勝利後は以後の進行を停止します。

## 既存プロトタイプ盤面の扱い

盤面・移動・柵の設置条件は既存プロトタイプを維持し、視界計算をSYS-VISION-001に置き換えています。以下の盤面値を正式なフィールド仕様として確定したものではありません。

- 段差盤面は A=3、B=4、C=5、D=6、E=7マス、計25マス。左オフセットは A=2、B=1、C=1、D=0、E=0。
- 囚人は既存の任意マスへ配置でき、同居も可能。
- 右・上・下の既存隣接判定を使用し、段差外・斜め移動は不可。
- A2/B3/C4/D5/E6から既存の「右へ／脱獄」で脱獄。
- 柵は共有境界へ配置。初期5本は B0・C0・C2・D4・E2 の北側境界。初期柵も破壊可能。
- 柵・囚人による移動妨害は追加せず、横向き境界柵を視界の前面柵へ対応付け。
- 捕獲・復帰の新ルールは追加せず、既存 `Prisoner` の捕獲処理を使用。

main の強制配置、行動直後の自動ターン終了、全員勝利不能時の「勝者なし終了」は、今回の確定済みフローに従って除去しました。

## 未確定時の停止と再確認

スキル山札と使用済みがともに空の場合はドローを省略せず理由を表示して停止します。必要な対応計画・複数所有者順がない場合、明示的な監視上書きが結果を供給できない場合も同様です。監視供給元の未指定は停止理由ではなく、標準山札を使用します。「設定を再確認」は再試行可能な待機について設定を再評価します。

看守の初期フィールドが未設定または既存盤面と不整合の場合は、正式な配置値を推測せず仕様待機にします。設定を修正して、表示される再確認・初期化手順に従ってください。

効果解決中に新しい即時発動が発生した場合や、効果内で山札と使用済みがともに空になった場合、未定義の優先順位を決めて残りの解決を進めません。途中適用状態を保持して停止します。**途中状態からの再開は未実装**です。関連仕様と設定を修正後、対局を再開始する必要があります。

## 検証

Play 中に `Tools > Daidatsugoku > Run Play Mode Checks` を実行します。対局を初期化し、明示的なテスト用カード・監視供給元・対応方針で検証して、設定を復元します。セーブ・通信・同期は既存 main に存在しません。

Unity `6000.6.6f1` の実シーンで、視界・監視v1.2・ターン・盤面・履歴UIを合わせた **1,824検証に成功**しています。純C#の視界計算・位置状態68件を含み、初期フィールド設定、連続反転、最新の柵、割り込み待ち中の視界未計算、解決後の1回のスナップショット取得、複数所有者の一括・変更不可通知、監視無効化を検証しました。監視無効化の許可を持たないカードは、初回応答と子チェーンの両方で拒否されることも確認しています。

`Logs/SYS-VISION-001-top.png` と `Logs/SYS-VISION-001-bottom.png` を表示し、1人の看守とTOP/BOTTOM・基準列のラベル、通常画面に視界の色分けがないことを確認しました。デバッグ機能は明示更新とキャッシュの自動検証に成功していますが、実SceneビューでのGizmos描画の手操作確認は未実施です。

正本SYS-VISION-001 v1.0第13章の全文は未提供のため、提示された実装指示書9章の12重点条件と式・具体例を検証対象としています。未提供の第13章全ケースを網羅したとは扱いません。Windows64 Developmentビルド成功（エラー0・警告496件）、グラフィック有効のPlayerを6秒起動して早期終了・スクリプト例外なしも確認しました。実装・暫定接続・検証範囲の詳細は `Tools/SYS-VISION-001-v1.0-report.md` を参照してください。

監視v1.2単体段階では、Unity実シーンで既存ゲームフロー・盤面・HUDと山札・履歴・外部サービス連携を合わせた1707検証に成功しています。これは視界v1.0を追加する前の記録であり、今回の再検証結果とは区別します。

バッチで視界を含む実シーン検証を行う場合は、Unityに `-batchmode -projectPath C:\DevGame\TOKAI2 -executeMethod GuardValidationBatch.RunVision -logFile Logs/SYS-VISION-001-unity.log` を渡します。検証は非同期に進み完了時に自動終了するため、`RunVision` に `-quit` は付けません。試作フィールドの設定をバッチで行う場合は、`-batchmode -quit -projectPath C:\DevGame\TOKAI2 -executeMethod GuardVisionSceneSetup.ConfigurePrototype -logFile Logs/SYS-VISION-001-setup.log` を使用します。

過去の監視v1.2単体段階のG-001～G-018対応とビルド結果は `Tools/SYS-GUARD-001-v1.2-report.md` に保存しています。今回のPR作成はユーザーの指示により保留しています。
